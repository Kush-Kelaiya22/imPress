# Risk register

The findings of the *imPress v2.2 Security, Privacy & Compliance Audit* (14 October 2026, reviewed at PR #195 head 9dfd663) and where each stands in this release. Status words: **fixed** (the control exists and is tested), **mitigated** (reduced, residual risk named), **open** (not done), **external** (needs someone else's action). Owners are roles: assign names in your copy.

| ID | Finding | Status | What changed | Residual risk | Owner | Issue |
|---|---|---|---|---|---|---|
| A1 | A single super admin could accept an altered database as trusted, reset the system and erase the local audit trail | **mitigated** | dual control with step-up, delay, expiry and single use; reset cannot delete recent audit entries; external hash-chained audit trail; policy owned by root | root or host compromise; two super admin accounts controlled by one person; step-up is a password, not multi-factor | system owner | [#196](https://github.com/Kush-Kelaiya22/imPress/issues/196) |
| A2 | CSP allows inline JavaScript | **fixed** | every inline handler replaced by delegated events; `script-src 'self'`, `script-src-attr 'none'`; violations reported; quote-escaping fixed and tested; a browser test asserts no violations on any page and that injected inline script is blocked | style attributes still need `style-src 'unsafe-inline'` (low risk) | application lead | [#197](https://github.com/Kush-Kelaiya22/imPress/issues/197) |
| A3 | Device traffic can use HTTP by default | **mitigated** | the hardened profile requires device HTTPS and per-device keys and will not start otherwise | boards must be built and configured for TLS; hardware checks not run | system owner | [#198](https://github.com/Kush-Kelaiya22/imPress/issues/198), [#92](https://github.com/Kush-Kelaiya22/imPress/issues/92) |
| A4 | Mesh frames are not authenticated; replay possible | **open** | design proposal only | a nearby device can forge or replay an answer: run pilots in a controlled room and label results spoofable | firmware lead | [#187](https://github.com/Kush-Kelaiya22/imPress/issues/187) |
| A5 | Firmware signing, TLS and secure boot are optional | **mitigated** (server) / **open** (boards) | the hardened profile requires a site signing key, no unsigned images, separate uploader and approver | no secure boot or flash encryption on boards; private signing key must be kept off the server | firmware lead | [#199](https://github.com/Kush-Kelaiya22/imPress/issues/199) |
| P1 | No privacy notice, data inventory, rights process, retention or breach playbook | **mitigated** | this toolkit | templates need your decisions, a legal review and drills | privacy lead | [#200](https://github.com/Kush-Kelaiya22/imPress/issues/200) |
| P2 | Debug mode copies production data with no expiry | **mitigated** | root can disable it (off when hardened), expiry by policy, private permissions, every action audited, signed exports | copies are not encrypted at rest | system owner | [#201](https://github.com/Kush-Kelaiya22/imPress/issues/201) |
| P3 | Logs and backups are local and mutable; no retention or incident process | **mitigated** | external audit sink, retention flags, expiry of copies, backup script, runbooks | your off-host storage must really be immutable and administered by someone else | system owner | [#202](https://github.com/Kush-Kelaiya22/imPress/issues/202) |
| P4 | Self-repair can restore a stale copy and loses evidence | **fixed** | the failed database is kept before restore; the alert states the backup's age; accepting a state needs approval | up to one check interval of valid changes is lost on a restore | system owner | [#203](https://github.com/Kush-Kelaiya22/imPress/issues/203) |
| D1 | Published docs 'latest' pointed at the old base | **external** | docs and release notes updated | the Read the Docs project setting must follow the release | docs owner | [#209](https://github.com/Kush-Kelaiya22/imPress/issues/209) |
| N1 | Hardware evidence missing for SPI, radio, TLS, signed OTA, rollback | **open** | software tests and simulators only | everything board-level is unproven until the hardware issues close | hardware tester | [#185](https://github.com/Kush-Kelaiya22/imPress/issues/185) and the `needs:hardware` issues |
| N3 | Any teacher could edit or deactivate any student and read every student's contact details (found in the permissions review) | **fixed** | the student scope: administrators, the teacher who registered the student, faculty of a class the student is in; contact details redacted outside it | a teacher can still find any student by name or number to enrol them | application lead | [#207](https://github.com/Kush-Kelaiya22/imPress/issues/207) |
| N2 | Student erasure left names in the activity log (found while implementing the audit sink) | **fixed** | erase scrubs the log, the erase entry holds a keyed reference, the sink never receives student personal data | backups and your own exports | privacy lead | [#200](https://github.com/Kush-Kelaiya22/imPress/issues/200) |

## How to use it

Review it each release. Accepting a residual risk means a named person writes the date and the reason next to it. The audit's production checklist is in [production hardening](../guides/production-hardening.md); each unchecked box there is a risk you are carrying.
