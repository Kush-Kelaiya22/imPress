imPress {{version}} is a release of the v{{line}} line. imPress is a classroom response system. Students answer quizzes and polls with small button modules. The teacher sees the answers live in a web app.

The v{{line}} line adds over-the-air (OTA) firmware updates with rollback, device health data, CSV imports, timed quizzes, per-device keys, signed firmware and TLS for devices. It also adds a container image for the server. Each change that reaches `varun/v2.1` and passes all tests is published as the next v{{line}} patch release.

## What is new in v{{line}}

| Area | Change |
|---|---|
| Quizzes | Timed quizzes advance and end automatically. The server refuses late answers. Modules with a display show a countdown. |
| Quizzes and polls | A completed quiz or a closed poll cannot start again. A draft cannot be stopped. |
| Imports | Import quiz questions, courses and sections from CSV files, with a preview before you save. |
| Firmware | A firmware registry that reads the target, chip and version from each image. |
| Updates | Staged OTA deployments (canary, batches, pause, resume, cancel). The gateway updates itself. Devices roll back a bad image automatically. |
| Devices | Health states and diagnostics: uptime, reset reason, boot count, free memory and hub link. A list of all student modules. |
| Security | Per-device keys. Optional signed firmware. Optional TLS between the devices and the server. |
| Database | Versioned migrations with an automatic backup before each upgrade. |
| Server | A tested install script and a container image. |

## Before you start

You need:

- A server on the same network as the classrooms: Linux x86_64 with Python 3.12 or later, or any host with Docker.
- One gateway per classroom: ESP32-C6 with 8 MB flash or more.
- One hub per classroom: ESP32-S3 with 32 MB octal flash. PSRAM is optional.
- Student modules: ESP32 with 4 MB flash and four answer buttons.
- ESP-IDF v6.1 to build the firmware with your settings. To flash prebuilt images only, you need `esptool` (`pip install esptool`).

The wiring and the pin map are in the [hardware reference](https://github.com/Kush-Kelaiya22/imPress/blob/{{tag}}/docs/reference/hardware.md).

## Set up the server

Use one of the two methods.

### Method A: install script

1. Download `impress-{{version}}.zip` and extract it.
2. Open a terminal in the `impress-{{version}}` folder.
3. Run the install script:
   ```bash
   scripts/install.sh
   ```
   The script creates a Python environment in `backend/.venv`. It also creates `backend/.env` with new random secrets.
4. Start the server:
   ```bash
   IMPRESS_HOST=0.0.0.0 scripts/start.sh
   ```
5. Find the line `Initial super admin created: username=admin password=...` in the log. Record the password. The server shows it one time only.
6. Open `http://<server-address>:8000` and log in as `admin`. Change the password immediately.

To run the server as a service, use the systemd unit in the [deployment guide](https://github.com/Kush-Kelaiya22/imPress/blob/{{tag}}/docs/guides/deployment.md).

### Method B: container

1. Start the container:
   ```bash
   docker run -d --name impress --restart unless-stopped \
     -p 8000:8000 -v impress-data:/data \
     ghcr.io/kush-kelaiya22/impress-backend:{{version}}
   ```
2. Read the log:
   ```bash
   docker logs impress
   ```
   Record the `admin` password and the device API key from the log.
3. Open `http://<server-address>:8000` and log in as `admin`. Change the password immediately.

The `/data` volume keeps the database, the uploaded firmware and the secrets. Back up this volume.

### Configure the server

- Keep the device API key (`IMPRESS_DEVICE_API_KEY`). Each gateway and hub needs it.
- To use HTTPS, follow [deployment: TLS](https://github.com/Kush-Kelaiya22/imPress/blob/{{tag}}/docs/guides/deployment.md).
- All settings are in the [configuration guide](https://github.com/Kush-Kelaiya22/imPress/blob/{{tag}}/docs/guides/configuration.md).

## Prepare the devices

Each board must know the Wi-Fi network, the server address and the device API key. Write these settings into the firmware when you build it.

1. Install ESP-IDF v6.1.
2. For the gateway, run:
   ```bash
   cd firmware/class_c6
   idf.py menuconfig
   ```
3. In **imPress C6 Gateway Configuration**, set the Wi-Fi name and password, the server address and port, and the device API key.
4. Connect the gateway with USB. Erase it, then build and flash it:
   ```bash
   idf.py -p <port> erase-flash flash monitor
   ```
5. Do steps 2 to 4 again for the hub (`firmware/class_s3`, menu **imPress S3 Class Module Configuration**). Use the same server and key.
6. Flash each student module from `firmware/student`. On the first start, enter the student's 10-character enrollment number with the buttons.

Important:

- Flash each gateway and each hub over USB one time with this release. This installs the bootloader that can roll back a bad update. After that, update them over the air.
- The prebuilt images in `impress-{{version}}-firmware.zip` contain the default settings. Use them for OTA uploads, or for boards that already have their settings. To configure a new board without a build, see [releases: flash prebuilt images](https://github.com/Kush-Kelaiya22/imPress/blob/{{tag}}/docs/guides/releases.md#flash-prebuilt-images).

## Test the installation

Do these tests before you use the system in a class.

1. Check the server:
   ```bash
   curl http://<server-address>:8000/health
   ```
   The result must show `"status":"healthy"` and `"version":"{{version}}"`.
2. Run the smoke test. It logs in, registers a test gateway and checks the main functions:
   ```bash
   python3 scripts/smoke_test.py --base http://<server-address>:8000 --password <admin-password>
   ```
   For the container, add `--device-key <device API key>`. The last line must be `smoke test passed`.
3. Optional: run the full test suite from the source folder:
   ```bash
   python3 run_tests.py
   ```
4. In the web app, open **Admin > Modules**. Make sure that the gateway shows `ONLINE` and that `s3_link_ok` is true.
5. Create a test class and activate it. Run a one-question quiz with two student modules. Make sure that each press shows one time in the live count.

The bench test plan for hardware is in [hardware validation](https://github.com/Kush-Kelaiya22/imPress/blob/{{tag}}/docs/testing/HARDWARE_VALIDATION.md).

## Deploy to a classroom

1. Create the courses and the classes. Give each class the room label (`classroom_code`) of its room.
2. Import the students from a CSV file, and enroll them in their classes.
3. Install the gateway and the hub in the room. Connect them to power.
4. Activate the class at the start of the lesson. The gateway connects to the active class of its room.
5. Give the students their modules. Make sure that each module shows `Connected!`.
6. Deactivate the class at the end of the lesson.

To update the firmware later:

1. Upload the new image on the **Firmware** page.
2. Approve the image.
3. Click **Deploy**. Start with one device (the canary), then continue in batches.

Do not update devices during a lesson. A device that cannot start the new image goes back to its previous image automatically.

## Upgrade from an earlier 2.1 release

1. Back up the database (Method A) or the `/data` volume (Method B).
2. Install {{version}} with the same method. For the container, start the new tag with the same volume.
3. Start the server. New database migrations run automatically, with a backup first.
4. Update the gateways and hubs from the **Firmware** page when the release notes say that their firmware changed.

## Upgrade from 2.0

1. Stop the 2.0 server.
2. Back up the database: `sqlite3 backend/impress.db ".backup 'impress-before-2.1.db'"`.
3. Install {{version}} with Method A or Method B. Keep your data:
   - Method A: before you run `scripts/install.sh`, copy `backend/impress.db`, `backend/.env` and `backend/firmware_bins/` from the 2.0 folder into the new `backend/` folder.
   - Method B: copy the same database, `.env` and `firmware_bins/` into the `/data` volume.
4. Start the server. It applies the database migrations (steps 1 to 8) automatically and writes a backup next to the database first.
5. If two classes have the same course and section, the upgrade stops and shows their names. Rename one of them, then start the server again.
6. Flash each gateway and each hub over USB one time (see **Prepare the devices**).
7. Devices get their own keys automatically on their next registration. When **Admin > Modules** shows the key state `active` for all devices, you can set `IMPRESS_DEVICE_KEYS_REQUIRED=true`.

### Roll back

- **Server:** stop the server. Restore the database backup. Start the previous version.
- **Devices:** deploy the previous image from the **Firmware** page, with the downgrade option. The [recovery procedure](https://github.com/Kush-Kelaiya22/imPress/blob/{{tag}}/docs/firmware/RECOVERY_PROCEDURE.md) gives all cases.

## Known limits

- The hardware tests for this release are not complete. The release status at the top of this page shows the open test issues.
- Student modules do not have OTA updates. Update them over USB.
- The mesh between the modules and the hub is not encrypted.
- Signed firmware and device TLS are off by default. Turn them on before production use.
- The container image is for linux/amd64 only.

More: [known issues](https://github.com/Kush-Kelaiya22/imPress/blob/{{tag}}/docs/reference/known-issues.md).

## Verify the downloads

Put the files in one folder and run:

```bash
sha256sum -c SHA256SUMS.txt
```

Each file must show `OK`. Each firmware folder also has its own `SHA256SUMS` file.
