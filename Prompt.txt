# Task: imPress Hardware Deployment, Firmware Flashing, and End-to-End Integration Testing

You are working on **imPress**, an ESP32-based classroom participation system. Your task is to deploy the existing firmware onto three physically connected ESP32 devices, connect them to the running backend, and thoroughly test the complete hardware-to-software communication pipeline.

This is a real hardware integration and debugging task, not a request to redesign or rewrite the project.

Work autonomously wherever possible. Inspect the repository, understand its architecture, identify the correct firmware and configuration files, execute the necessary commands, diagnose failures, and apply minimal, justified fixes.

## 6. Test the complete communication pipeline

The expected architecture is:

Student Module → ESP-NOW → ESP32-S3 Hub → SPI → ESP32-C6 Gateway → Wi-Fi → FastAPI Backend → Teacher/Admin Web Interface

Verify each connection individually before performing end-to-end testing.

### A. Student module → S3 hub

Check:
- ESP-NOW initialization
- Device discovery and enrollment
- Peer registration
- Channel compatibility
- Packet transmission and reception
- Response payload validity
- Sequence numbers and duplicate handling
- Packet loss and retransmission behavior, where implemented

### B. S3 hub → C6 gateway

Inspect and validate the existing SPI interface, including:
- Master/slave roles
- Configured GPIO mappings
- SPI initialization
- Clock frequency and compatibility
- Existing 4096-byte frame contract, if still applicable
- Ready/handshake signals
- Buffer management
- Frame boundaries
- Payload integrity
- Timeout and recovery behavior

Do not change SPI pins, clock settings, or frame structures without verifying both firmware implementations and the hardware specifications.

### C. C6 gateway → Backend

Verify:
- Wi-Fi association
- DHCP/IP assignment
- Backend reachability
- Device authentication
- HTTP request formatting
- Batch submission
- WebSocket connection and authentication
- Heartbeats
- Reconnection after temporary network failure
- Appropriate logging and error handling

Inspect the backend to determine which requests should produce database entries and UI updates.

### D. Backend → Web Interface

Open or test the provided admin interface using supported browser tooling, if available.

Verify that:
- The backend is responding.
- The gateway can authenticate.
- The applicable devices appear in the inventory or diagnostic interface.
- Connectivity and presence indicators reflect real device activity.
- An authorized teacher/admin can create or use a test class and session.
- Responses submitted by a student module are reflected correctly in the appropriate interface.

Do not mistake successful page loading for successful end-to-end integration.

## 7. Perform end-to-end functional tests

Use existing test infrastructure and authorized test accounts.

Where hardware interaction is required, use actual physical input or a documented test mechanism. Do not claim that physical buttons were pressed if only simulated packets were used.

Test the following scenarios when supported:

| Test | Expected result |
|---|---|
| Gateway boot | C6 initializes and connects to the backend |
| Hub boot | S3 initializes ESP-NOW and SPI |
| Student boot | Student module initializes correctly |
| Device enrollment | Student module becomes recognizable to the system |
| Single response | One valid response reaches the backend |
| Duplicate response | Duplicate is handled according to the protocol |
| Multiple responses | All valid responses are processed correctly |
| Invalid payload | Rejected or handled without crashing |
| Gateway Wi-Fi interruption | Gateway reconnects as designed |
| Backend temporarily unreachable | Firmware handles the failure safely |
| S3 restart | Communication recovers as specified |
| Student restart | Device reconnects or re-enrolls as appropriate |
| Repeated responses | No unexpected corruption, memory growth, or crashes |
| UI updates | Submitted responses appear correctly in the intended session |

Use actual observations to classify each test as PASS, FAIL, BLOCKED, or NOT RUN.

## 8. Debugging and corrective action

If a test fails:

1. Identify the exact failing stage.
2. Capture the relevant logs and error messages.
3. Determine whether the root cause is firmware, hardware, network, protocol, backend, or configuration.
4. Inspect the relevant source code.
5. Apply the smallest technically sound correction.
6. Rebuild and reflash affected devices when appropriate.
7. Repeat the failed test.
8. Run relevant regression tests.

Avoid speculative changes and large rewrites.

In particular, investigate:
- ESP32-C6 boot/reset behavior
- ESP32-S3 Wi-Fi/ESP-NOW initialization sequence
- SPI synchronization and frame handling
- Device authentication and enrollment
- Backend/device WebSocket compatibility
- Packet duplication and loss
- Firmware version mismatches

Do not silently reduce security, disable validation, or remove functionality merely to make tests pass.
